# LeetBuild — build systems, step by step

LeetCode for systems, with an **AI-era interview track**. Each course is a real system cut down to the parts that transfer — a URL shortener, a rate-limited API gateway, an image cache microservice, live chat fan-out, a notification service, a match engine, an online merchant transaction system, flash-sale inventory, a news feed, ride dispatch — built one file at a time in Python, TypeScript, Go, Scala or C++. Six more are **company tagged**: derived from engineering blogs (Reddit's r/place, Netflix's distributed counters, Discord's message storage, Stripe's ledger, Dropbox's feature gates, DoorDash's LLM support assistant), with the sources linked. Every step exercises one of four concepts: **HTTPS servers, gRPC, Kafka, Redis**.

The AI-era track — **LLM Gateway** and **RAG Service** — is built around the skills AI-era interviews probe: can you specify a task, delegate to a model, review what it produced, measure quality, and keep the result safe and affordable? Every starter in that track is a plausible model-generated draft with a real flaw. You review it, fix it, and the checks prove the fix. The landing page gives the track its own section and rubric, and a header switch moves between the catalogue and **`/mock-interview`**, a timed practice loop with the same flawed drafts, an offline AI pair and a report.

A step gives you a task, a sequence diagram of the interaction, interactive infographics (TLS/HTTP lifecycle, status codes, idempotency keys, gRPC call types, deadlines and retries, Kafka partitions, consumer groups, delivery semantics, cache-aside and stampedes, token buckets, the transactional outbox, a limit order book), three progressive hints, and a revealable reference solution (plain or as a diff against your code). The architecture diagram highlights the components the step builds; click one to jump to its step.

## Run it

```sh
yarn install --ignore-engines   # node 22.10 is a hair below what one transitive eslint dependency declares
yarn dev                        # http://localhost:3000 (builds the runtime workers first)
yarn build && yarn start        # production
yarn verify                     # checks every course (see below); run after editing content
yarn verify --no-runtime        # the same without executing the Python and TypeScript harnesses
yarn verify --runtime typescript   # execute only one language's harnesses
yarn lint                       # prettier --check + eslint, as CI runs them
yarn format                     # prettier --write + eslint --fix
yarn compile                    # tsc --noEmit
yarn build:runtime              # rebuild public/py/worker.js and public/ts/worker.js after editing src/lib/runtime/
yarn protogen <course dir>      # regenerate a course's Python protobuf modules and .proto sources from proto/*.proto
```

Without yarn, the same scripts run through npm: `npm install --no-package-lock`, `npm run dev`,
`npm run build`, `npm run verify`. `predev`/`prebuild` invoke the local `tsx` binary, so no global
tool is needed.

Set `NEXT_PUBLIC_SITE_URL` (see `.env.example`) to the public origin when deploying: it is used for the canonical link and for the URLs inside shared result cards and exported Markdown. Without it, share links use the page's own origin.

## How it works

- **Python runs in the browser** (`src/lib/runtime/`, `public/py/`). A submission in Python is executed, not just pattern-matched: a Web Worker boots Pyodide (CPython in WASM, from the jsDelivr CDN, ~10 MB cached after the first run) into the LeetBuild runtime, which provides the infrastructure the courses talk to without a network — Redis through `fakeredis` on the virtual clock (TTLs, pub/sub, pipelines, GEO, and Lua scripts executed by a fengari VM on the JS side), an in-memory Kafka broker behind a `confluent_kafka`-shaped client (partitions, consumer groups, commits, delivery callbacks, and a broker that can stall: `poll(t)`/`flush(t)` wait on the virtual clock and unacknowledged records time out after `message.timeout.ms`, as librdkafka does), gRPC over an in-process transport that generated `*_pb2_grpc` stubs and `grpc.aio` servers plug into (deadlines, latency and failure injection, streaming, cancellation, and instances at addresses — a channel reaches the instance it dialled, a stopped one answers `UNAVAILABLE`), and real Postgres through PGlite (pgvector included). Each step's **harness** (`Step.harness.python`, one `check_<id>(ctx)` per check) runs the step inside the course's real system: the step's own file is the learner's, so is every step they have passed in that language, and every other step runs its reference implementation — the code under test talks to real neighbours, never to stubs (`yarn verify` mounts the reference for every other step). Checks grade outcomes only — responses, return values, Redis/Kafka/Postgres state, the order and timing the resources saw — and inject faults the way production does: a stalled broker, a slow or dead instance, a broken table, a second worker's request landing between two of the learner's Redis commands (`ctx.redis_after`, which is how a check-then-set race is caught); the harness has no access to the learner's source. The runtime verdict decides acceptance and the static pattern check survives only as an advisory _shape_ chip. A run that cannot complete (runtime failure, 20 s budget) is reported, not counted as a wrong submission. The Python runtime itself lives in `public/py/runtime/` (plain `.py` files) and is shared with `yarn verify`, which runs every harness in Node.
- **TypeScript runs in the browser too** (`src/lib/runtime/typescript.ts`, `src/lib/runtime/ts/`, `public/ts/`). Its worker boots esbuild-wasm (from the CDN, ~14 MB cached after the first run) and transpiles the learner's files, the course's support modules and the step's harness to CommonJS modules it executes itself — the "WASM" realism comes from the resources, not from a second interpreter: the same PGlite Postgres, Lua through the same fengari VM, and TypeScript models of the rest shaped like the libraries a Node service uses — `ioredis` over an in-process Redis (strings, hashes, lists, sets, sorted sets, GEO, pub/sub, MULTI/EXEC, pipelines, EVAL, expiry on the virtual clock), `kafkajs` over the same broker semantics as the Python runtime (partitions, groups, commits, auto-commit timers, `acks`, idempotence, stalls, lost acks, failover), `@grpc/grpc-js` + `@grpc/proto-loader` over an in-process transport that parses the course's `.proto` at run time (unary and all three streaming shapes, deadlines, latency and failure injection, instances at addresses), a Fastify-shaped HTTP layer driven through `app.inject`, and `pg`'s `Pool`/`Client`. `Date.now`, `setTimeout` and `setInterval` run on a virtual clock while a check runs: a sleep is free, latency and stalls cost only the caller that awaits them, intervals fire as time passes, and a loop that never ends is stopped after its sleep budget. `Step.harness.typescript` has the same contract as the Python one (`ctx.load`, `ctx.redis`, `ctx.redisAfter`, `ctx.db`, `ctx.kafka`, `ctx.grpc`, `ctx.clock`, `ctx.client(app)`, `ctx.drain`), and `yarn verify` runs it in Node with the native esbuild.
- **The static judge** (`src/lib/judge.ts`) remains the verdict for Go, Scala and C++ and the advisory layer for Python and TypeScript. Every step lists named checks — properties a correct implementation has (the route, the TTL, the `NX` on the lock, the commit _after_ the side effect) — as per-language patterns evaluated on comment-stripped code with `all` / `none` / `order` semantics. From the second wrong submission on a step, each failing static check also shows the shape the judge expects (`describeMatcher`).
- **Run and Submit**: where the code executes (Python, TypeScript), _Run_ (`⌘'` / `Ctrl+'`) exercises the step's first check — the example, marked as such in the checks list — against your files and reports what the harness observed, the program's output included, with nothing recorded: no wrong submission, no history entry, no score. _Submit_ (`⌘⏎`) runs every check and counts. Every submission keeps the code it judged: the step's Submissions list opens any of them read-only, shows the edits since as a diff against the editor, and puts it back (an in-place replacement, so undo reverses it).
- **Against the reference** (`src/lib/metrics.ts`, `RunMetrics` in `src/lib/runtime/types.ts`): under an accepted run, _compare_ runs the reference solution in place of your file — same checks, same neighbours, same world — and sets side by side what each did, counted by the runtime's resources while every check ran: Redis round trips and commands, records produced, consumed and committed, RPCs made, SQL statements, virtual waits and the time they covered. The harness's own calls are left out (its Redis reads, its `ctx.db.execute`, its calls into your servers), seeded records are not "produced", and both runtimes count the same things, so the figures are deterministic and comparable across languages; a difference is in the code, not in the weather — the opposite of a "beats X%" percentile. Informational only: no verdict or score depends on it.
- **Scoring** (`src/lib/scoring.ts`) is contest-like: 7 / 10 / 19 points per step by difficulty — the live maximum is the sum over every course (`profile.max`), so adding content never requires re-balancing; the original eighteen courses, AI-era and company-tagged ones included (98 steps: 19 easy, 33 medium, 46 hard), totalled exactly 1337 and the catalogue grows from there (certificates carry the maximum they were earned under, so a growing table never rewrites an issued one) — −20% per hint, −5% per wrong submission (floor 25%, rounded to whole points), 0 for a revealed step. Totals roll up into a guild rank (Novice → Apprentice → Journeyman → Artificer → Master Artificer → Archmage, by share of all points), solved counts by difficulty (the LeetCode-style Easy / Medium / Hard `x/y` block on the landing strip; a problem is solved when every step is accepted) and per-concept mastery. Steps unlock in order; a course can be started over.
- **Company-tagged courses** (`src/data/companies.ts`, `Problem.company` / `Problem.sources`): courses derived from a company's published engineering writing — r/place (Reddit), Distributed Counters (Netflix), Message Storage (Discord), Ledger (Stripe), Feature Gates (Dropbox), Support Assistant (DoorDash). They sit in the systems track with the other courses of their difficulty, marked with the company's chip: its own logo beside its name (the official marks as traced by Simple Icons from each brand page — CC0 path data, trademarks of their owners — in the colours the brand guidelines give: Reddit's orange Snoo bubble, the red Netflix N, Discord's Blurple Clyde, Stripe's white S on its purple tile, Dropbox's blue boxes, DoorDash's red arrow). Each course page opens with the company's logo and publication and ends with a **Sources** section linking every post with its date, byline and what the course takes from it, and the statement has a _From the source_ section paraphrasing the post. `yarn verify` enforces company ⇔ sources, https links, dated entries and the section; the Markdown export carries the sources too.
- **AI systems without a model** (`src/data/problems/15-doordash-support/`): the Support Assistant course grades the system around an LLM, not the LLM. The model server and the LLM judge are deterministic stand-ins the harness serves over gRPC (`assistant/model`: the faithful mode cites the chunks it was given, the hallucinating one invents a policy and a chunk that was never retrieved, the verbose one needs `max_tokens` to cut it); embeddings are TF-IDF vectors over the knowledge base's vocabulary (`assistant/embed`, the same numbers in Python and TypeScript); retrieval is real pgvector in Postgres; and the checks assert what a system can guarantee — grounding, limits, deadlines, fallback, escalation to a human, exactly-once scoring — never prose quality.
- **Game layer** (`src/lib/gamify.ts`, `src/components/Badges.tsx`): 25 badges in six tracks (Milestones, Craft, Mastery, Habit, Languages, Timed), each with measurable _progress_ ("Kafka master 3/16", "Shipped 4/6 · Image Cache", "Clockwork 3/15 problems") — a badge is earned exactly when its progress completes, badges are never revoked, and fresh ones are announced with toasts. The Timed track is earned from _counted_ runs (completed within the budget, nothing revealed): the first one, one under the Tight ¾× budget, a sprint in half the budget, a photo finish with under a minute left, a hard problem under Tight, five problems under Tight, every problem under Tight. A daily streak (3, 7 and 30 days are badges) comes with the **step of the day**: a step you can open right now — each unfinished course's next one — picked by the date with rendezvous hashing, so it stays put while other courses move and only changes when it is done; behind the strip's stats, a year's **heatmap** of accepted steps per day with active days and best streak (`activityByDay`, `src/components/Heatmap.tsx`). Also progress to the next rank; confetti on every fresh accept; a Wordle-style result card per course that `share` posts to LinkedIn. The landing page keeps all of this to one strip — points inside a rank ring, the streak with what to do about it, the badges earned, one row of concept mastery — with the full catalog (closest badges first) and the secondary stats one click away, so the problems stay above the fold.
- **Timer mode** (`src/lib/timer.ts`, `src/components/Timer.tsx`): the timer lives in the header, in one pill, so the problem pane stays about the problem. At rest the pill shows the time a run starts with — the problem's estimate, `45:00` — and a click starts one: pick a budget (¾×, 1× or 1½× the estimate), the problem is reset and the clock starts from step 1; the same pill is then the countdown (amber under five minutes, red in the last minute), survives reloads, and ends the run early when clicked; its chevron opens the problem's run history and its tooltip names your best counted time. The run ends when every step is done; when the budget runs out you choose between ending it and keeping going, in which case the clock counts up (`+m:ss over`) and the run is recorded but not counted. A run _counts_ only when the problem is completed within the budget with no solution revealed — that time appears on the problem's row; every run, newest first with how it ended, is one click away from the landing strip and from the pill.
- **Scratchpad** (`src/lib/scratchpad.ts`, `src/components/Scratchpad.tsx`): a whiteboard in a floating window over the playground (`⌘;` / `Ctrl+;`, or the pencil in the header) for sketching the system while building it — drag it by its title bar, resize or maximise it, keep reading the task and typing in the editor beside it. Boxes, ellipses and diamonds with centred labels (click to place one and type), arrows and lines that attach themselves to box outlines, freehand pen, text, an eraser; select, move, resize, drag connector ends, marquee-select, duplicate, nudge with the arrow keys; nine palette colours (the four concept hues among them), three widths, tinted fills, a dot grid with snapping; pan and zoom (wheel, pinch, space-drag); undo/redo; PNG export; and _course diagram_, which turns the problem's architecture diagram into editable boxes and arrows with the pane's routing and labels. One sketch per course (plus one for the landing page), persisted beside the workspaces.
- **Sharing and certificates** (`src/lib/social.ts`, `src/lib/certificate.ts`, `src/components/Social.tsx`, `src/pages/certificate/[course].tsx`): every badge toast, every earned badge in the catalog and every accepted step offers _Share on LinkedIn_ — LinkedIn's composer opens prefilled with an editable post; nothing is posted on the learner's behalf. A course completed with every step accepted (no solution revealed) earns a **certificate**: a PNG drawn on a canvas (name, course, concepts, date, score, timed-run time, a certificate id), downloadable from the course page, with _Add to LinkedIn profile_ (LinkedIn's certification deep link, filed under Licenses & certifications) and _Share on LinkedIn_. Each certificate has a public page, `/certificate/<course>?n=…&d=…&id=…`, pre-rendered per course with OpenGraph tags so the link unfurls; the learner's details travel in the query string and the id is a hash of them — there is no server and no record of learners. The name typed once is remembered.
- **Keyboard shortcuts** (`src/components/Shortcuts.tsx`): ⌘/Ctrl+⏎ submit, ⌘/Ctrl+' run the example check, ⌘/Ctrl+B explorer, ⌘/Ctrl+\ problem pane, ⌘⇧F / Ctrl+Shift+F **focus** (explorer and problem pane fold together and come back to how they were), ⌘/Ctrl+; scratchpad, ⌥/Alt+] and ⌥/Alt+[ next and previous step, `?` for the list (also behind the keyboard button in the header).
- **Editor settings** (`src/lib/editorSettings.ts`, `src/components/EditorSettings.tsx`): the gear in the editor bar — font size, long lines (scroll or wrap), key bindings (default or **Vim**, via `@replit/codemirror-vim`, with its status line under the editor). One set for every editor on the page, applied live through a CodeMirror compartment, remembered in `localStorage` (`leetbuild:editor`).
- **Report a step** (`src/lib/report.ts`): _report it ›_ under a step's checks opens a GitHub issue prefilled with the step, its URL, the language, the browser and the last verdict (failing checks and their messages); the learner's code is never attached — the template asks for it only when the verdict itself is in question.
- **Markdown export** (`src/lib/export.ts`): `⤓ download .md` on a course page saves its tutorial in the current language — statement, Mermaid architecture and sequence diagrams, tasks, checks, starters, hints and solutions behind `<details>` spoilers.
- **Persistence** (`src/lib/storage.ts`): attempts, language, per-step workspaces and per-course scratchpads live in IndexedDB (localStorage fallback) — per browser, no server.
- **Filesystem**: a course in a language is one virtual filesystem, one file per step (`thumb_server.py`, `thumb_cache.py`, …). The explorer beside the editor lists every file from step 1 with its status (✓ accepted, ◐ revealed, ○ open, 🔒 locked); clicking one opens it in a tab, VS Code style — tabs are the open files, closable with ×, and the step's own file opens itself when the step does. Every unlocked file is editable from any step and keeps its own undo history, so the code written in step 1 is there, as written, in step 2. The step's own file is marked with a dot and is the one Submit judges, whichever tab is active; `reset` restores the active file's starter. The explorer and the problem pane each fold away (the toggle left of the tabs, the `‹` in the pane header; a collapsed pane is a strip with the step title) and the choice persists with the layout in `localStorage` (`leetbuild:layout`).
- **Routes** (`src/pages/[[...slug]].tsx`): `/` is the problem list, `/<course>` reopens a course on the step last visited, `/<course>/<n>-<step>` addresses step n (numbered like its source file, e.g. `/image-cache/2-cache-aside`); every path is pre-rendered from the course data and anything else is a 404. Moving between them is ordinary navigation, so Back and Forward retrace your path while the playground stays mounted.
- **Finding a course** (`src/lib/catalog.ts`, `src/lib/listQuery.ts`, `src/components/ListControls.tsx`): one toolbar above the list, as LeetCode lays it out — a search pill (every word must appear somewhere in the title, tagline, company, concepts or step titles: `idempotency` finds the three courses with such a step), a sort menu (catalogue order, difficulty, points, estimate, progress, title; picking the current one again reverses it) and a filter menu (difficulty, status — not started / in progress / solved — and company-tagged), each button carrying a dot while it is in effect; at the right, `n/15 solved` with a ring, or `7 of 15 · clear` while filtering. The state is the URL — `/?q=redis&difficulty=hard&status=started&sort=points` — written with a shallow replace, so a view is a link and the plain landing stays `/`; rows keep their catalogue number whatever the order, and an empty result says so with the same way out.
- **Diagrams** (`src/lib/layout.ts`): architecture diagrams are laid out automatically from the call graph (layered left to right, boxes sized to text, labels in the column gaps, long edges detoured around boxes, back edges arched over everything they span, the edges into and out of a box spread along its side so arrowheads never stack; wide diagrams keep a readable size and scroll sideways). Sequence diagrams are drawn from each step's `sequence`.
- **UI** (`src/components/`): the playground shell with LeetCode-style drag gutters (`SplitGutter`), the problem list and profile card, the problem/step pane, the verdict pane, the file tabs and CodeMirror step editor (`src/lib/editor.ts`), the diagrams, the Markdown dialect (`Markdown.tsx`: headings, callouts, lists, fenced code, tables, `:::widget name {json}`, `:::details`, pop quizzes), and `widgets/` (one component per infographic, registered in `widgets/index.tsx`).
- **Themes** (`src/styles/palette.ts`, `src/lib/theme.ts`): Night and Day are two palettes of one shape — Day keeps every Night hue with its lightness solved for the same WCAG contrast targets on white — emitted as CSS variables by `tailwind.config.ts`, so Tailwind classes, the CodeMirror theme and the SVG diagrams switch live. The sun/moon button in the header toggles them; the choice is saved in `localStorage` (`leetbuild:theme`), applied before first paint by an inline script in `_document.tsx`, and until one is made the OS preference applies.

## AI-era interview track

The track is a practice thesis, not a relabel. AI-era interviews are shifting from "can you write
the algorithm?" to "can you use a model and still own the result?" The two courses are graded on six
behaviours a candidate can practise:

| Signal       | What the learner has to do                                                                   | Where it shows up                                                                                                                    |
| ------------ | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Specify**  | Turn an ambiguous ask into interfaces, limits and acceptance criteria.                       | Gateway request contract and token budget; RAG ingest contract and idempotency key.                                                  |
| **Delegate** | Use a model or provider where it helps, with explicit versions, deadlines and fallbacks.     | Provider calls, embedding batches, prompt and model versions.                                                                        |
| **Verify**   | Review the generated draft, test the edge cases, and reject what cannot be proven.           | Every starter is a plausible AI draft with a real flaw; citations must be literal substrings; eval metrics are computed from labels. |
| **Evaluate** | Build a golden set, calibrate the judge, gate a release on evidence.                         | RAG eval gate: 200-sample minimum, groundedness 0.95, recall@k 0.90, >1% regression blocks.                                          |
| **Secure**   | Treat retrieved text and tool output as untrusted; scope every tenant boundary.              | Tenant-scoped Redis keys and retrieval, prompt-injection boundary, no prompts or message text in usage/analytics events.             |
| **Operate**  | Bound cost, latency and failure with budgets, deadlines, retries, outboxes and commit order. | Atomic token reservation, 8s provider deadline, 2s embedding deadline, bounded retries, outbox fallback, commit after processing.    |

The AI-era courses (`src/data/problems/16-ai-gateway/`, `17-rag-service/`) currently use the static
review judge in all five languages; their runtime harnesses are the next content investment. The
classic courses keep the Python and TypeScript harnesses described above.

## Mock interview mode

`/mock-interview` is the timed practice loop, linked from the header switch and from the AI-era
section. A scenario opens with an interviewer brief and a plausible, flawed AI draft; the learner
has 20–25 minutes and an **offline AI pair** (draft, review, reveal the flaw, test idea), plus a
button that copies a review prompt for the learner's own AI assistant. Submit grades the step with
the same static checks the course uses. Accepted or not, the report shows the checks, what the AI got
wrong, follow-up questions, a debrief and copyable notes. There is no login, no hosted model, no
solution reveal and no effect on course points: it is a practice session, not an assessment product.

The four scenarios live in `src/data/mock.ts` and point at real AI-era steps:
`ai-gateway/tenant-budget`, `ai-gateway/streaming-cancel`, `rag-service/hybrid-retrieve` and
`rag-service/grounded-answer`.

## Content

Courses live in `src/data/problems/<NN>-<id>/`: `index.ts` holds the metadata, statement, architecture diagram (nodes, kinds and edges — placement is automatic), step order and the runtime **support modules** (`support.python`: generated protobuf code from `proto/*.proto` via `yarn protogen`, plus hand-written helpers in `support.ts`; `support.typescript`: the `.proto` sources themselves plus the TypeScript helpers); `steps/<k>-<step-id>.ts` holds one step: task, sequence diagram, hints, checks, starter/solution code in all five languages, and the **harnesses** (`harness.python`, a module with `check_<id>(ctx)` per check, `ctx` documented in `public/py/runtime/leetbuild/harness.py`; `harness.typescript`, a module exporting `check_<id>(ctx)` per check, `ctx` documented in `src/lib/runtime/ts/harness.ts`). Courses are ordered in `src/data/problems/index.ts`; the content model is `src/lib/types.ts` and the widget catalog `src/lib/widgets.ts`. Generating protobuf modules needs `python3 -m pip install grpcio-tools==1.81.0` (its gencode matches the protobuf runtime Pyodide ships).

`yarn verify` (or `--problem <id>` / `--file <path>` / `--verbose` / `--no-runtime` / `--runtime <language>`) runs the judge's self-tests, checks every course's shape (including that no two steps of a course own the same file in any language, and that every check of a step with a harness has its `check_` function), asserts for every step in every language that the starter fails at least one static check (and at most one passes already) while the reference solution passes them all, boots the Python and TypeScript runtimes in Node and asserts for every harness that the solution passes every runtime check while the starter does not, then checks that the course total is 1337.

Stacks the reference solutions use: Python — FastAPI, grpcio, confluent-kafka, redis-py · TypeScript — Fastify, @grpc/grpc-js + proto-loader, kafkajs, ioredis (pg for Postgres) · Go — net/http, google.golang.org/grpc, segmentio/kafka-go, go-redis v9 · Scala — Pekko HTTP, ScalaPB + grpc-java, kafka-clients, Jedis · C++ — cpp-httplib, grpc++, librdkafka, redis-plus-plus.

## Deploy

A plain Next.js 14 (pages router) app with no server-side state: deploy to Vercel or any Node host, or `next build` with static export. `NEXT_PUBLIC_SITE_URL` is optional: without it every share, certificate and export link is built from the page's own origin and the canonical/`og:url` tags are omitted; set it when the site answers on more than one origin (preview deployments, a vercel.app host beside a custom domain) so links and certificates always name the public one. The runtimes are static too: `public/py/` ships the Python worker bundle (built by `prebuild`), the runtime's `.py` files and two vendored wheels; `public/ts/` ships the TypeScript worker bundle; Pyodide, its packages, esbuild-wasm and PGlite are fetched by the browser from jsDelivr at first use.
