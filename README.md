# LeetBuild — build systems, step by step

LeetCode for systems. Each course is a real system cut down to the parts that transfer — a URL shortener, a rate-limited API gateway, an image cache microservice, live chat fan-out, a notification service, a match engine, an online merchant transaction system, flash-sale inventory, a news feed, ride dispatch — built one file at a time in Python, Go, Scala or C++. Four more are **company tagged**: derived from engineering blogs (Reddit's r/place, Netflix's distributed counters, Discord's message storage, Stripe's ledger), with the sources linked. Every step exercises one of four concepts: **HTTPS servers, gRPC, Kafka, Redis**.

A step gives you a task, a sequence diagram of the interaction, interactive infographics (TLS/HTTP lifecycle, status codes, idempotency keys, gRPC call types, deadlines and retries, Kafka partitions, consumer groups, delivery semantics, cache-aside and stampedes, token buckets, the transactional outbox, a limit order book), three progressive hints, and a revealable reference solution (plain or as a diff against your code). The architecture diagram highlights the components the step builds; click one to jump to its step.

## Run it

```sh
yarn install --ignore-engines   # node 22.10 is a hair below what one transitive eslint dependency declares
yarn dev                        # http://localhost:3000 (builds the runtime worker first)
yarn build && yarn start        # production
yarn verify                     # checks every course (see below); run after editing content
yarn verify --no-runtime        # the same without executing the Python harnesses
yarn lint                       # prettier + eslint
yarn compile                    # tsc --noEmit
yarn build:runtime              # rebuild public/py/worker.js after editing src/lib/runtime/
yarn protogen <course dir>      # regenerate a course's Python protobuf modules from proto/*.proto
```

Set `NEXT_PUBLIC_SITE_URL` (see `.env.example`) to the public origin when deploying: it is used for the canonical link and for the URLs inside shared result cards and exported Markdown. Without it, share links use the page's own origin.

## How it works

- **Python runs in the browser** (`src/lib/runtime/`, `public/py/`). A submission in Python is executed, not just pattern-matched: a Web Worker boots Pyodide (CPython in WASM, from the jsDelivr CDN, ~10 MB cached after the first run) into the LeetBuild runtime, which provides the infrastructure the courses talk to without a network — Redis through `fakeredis` on the virtual clock (TTLs, pub/sub, pipelines, GEO, and Lua scripts executed by a fengari VM on the JS side), an in-memory Kafka broker behind a `confluent_kafka`-shaped client (partitions, consumer groups, commits, delivery callbacks, and a broker that can stall: `poll(t)`/`flush(t)` wait on the virtual clock and unacknowledged records time out after `message.timeout.ms`, as librdkafka does), gRPC over an in-process transport that generated `*_pb2_grpc` stubs and `grpc.aio` servers plug into (deadlines, latency and failure injection, streaming, cancellation, and instances at addresses — a channel reaches the instance it dialled, a stopped one answers `UNAVAILABLE`), and real Postgres through PGlite. Each step's **harness** (`Step.harness.python`, one `check_<id>(ctx)` per check) runs the step inside the course's real system: the step's own file is the learner's, so is every step they have passed in that language, and every other step runs its reference implementation — the code under test talks to real neighbours, never to stubs (`yarn verify` mounts the reference for every other step). Checks grade outcomes only — responses, return values, Redis/Kafka/Postgres state, the order and timing the resources saw — and inject faults the way production does: a stalled broker, a slow or dead instance, a broken table, a second worker's request landing between two of the learner's Redis commands (`ctx.redis_after`, which is how a check-then-set race is caught); the harness has no access to the learner's source. The runtime verdict decides acceptance and the static pattern check survives only as an advisory *shape* chip. A run that cannot complete (runtime failure, 20 s budget) is reported, not counted as a wrong submission. The Python runtime itself lives in `public/py/runtime/` (plain `.py` files) and is shared with `yarn verify`, which runs every harness in Node.
- **The static judge** (`src/lib/judge.ts`) remains the verdict for Go, Scala and C++ and the advisory layer for Python. Every step lists named checks — properties a correct implementation has (the route, the TTL, the `NX` on the lock, the commit *after* the side effect) — as per-language patterns evaluated on comment-stripped code with `all` / `none` / `order` semantics. From the second wrong submission on a step, each failing static check also shows the shape the judge expects (`describeMatcher`); every step keeps a Submissions history.
- **Scoring** (`src/lib/scoring.ts`) is contest-like: 7 / 12 / 23 points per step by difficulty — all fourteen courses, company-tagged ones included (78 steps: 10 easy, 27 medium, 41 hard), are worth exactly 1337 and `yarn verify` enforces it, so adding a course means re-balancing the table (certificates carry the maximum they were earned under, so a re-balance never rewrites an issued one) — −20% per hint, −5% per wrong submission (floor 25%, rounded to whole points), 0 for a revealed step. Totals roll up into a guild rank (Novice → Apprentice → Journeyman → Artificer → Master Artificer → Archmage, by share of all points), solved counts by difficulty (the LeetCode-style Easy / Medium / Hard `x/y` block on the landing strip; a problem is solved when every step is accepted) and per-concept mastery. Steps unlock in order; a course can be started over.
- **Company-tagged courses** (`src/data/companies.ts`, `Problem.company` / `Problem.sources`): courses derived from a company's published engineering writing — r/place (Reddit), Distributed Counters (Netflix), Message Storage (Discord), Ledger (Stripe). They sit in the one problem list with the other courses of their difficulty, marked with the company's chip: its own logo beside its name (the official marks as traced by Simple Icons from each brand page — CC0 path data, trademarks of their owners — in the colours the brand guidelines give: Reddit's orange Snoo bubble, the red Netflix N, Discord's Blurple Clyde, Stripe's white S on its purple tile). Each course page opens with the company's logo and publication and ends with a **Sources** section linking every post with its date, byline and what the course takes from it, and the statement has a *From the source* section paraphrasing the post. `yarn verify` enforces company ⇔ sources, https links, dated entries and the section; the Markdown export carries the sources too.
- **Game layer** (`src/lib/gamify.ts`, `src/components/Badges.tsx`): 17 badges in five tracks (Milestones, Craft, Mastery, Habit, Languages), each with measurable *progress* ("Kafka master 3/16", "Shipped 4/6 · Image Cache") — a badge is earned exactly when its progress completes, badges are never revoked, and fresh ones are announced with toasts; a daily streak; progress to the next rank; confetti on every fresh accept; a Wordle-style result card per course that `share` posts to LinkedIn. The landing page keeps all of this to one strip — points inside a rank ring, the streak with what to do about it, the badges earned, one row of concept mastery — with the full catalog (closest badges first) and the secondary stats one click away, so the problems stay above the fold.
- **Timer mode** (`src/lib/timer.ts`, `src/components/Timer.tsx`): the timer lives in the header, in one pill, so the problem pane stays about the problem. At rest the pill shows the time a run starts with — the problem's estimate, `45:00` — and a click starts one: pick a budget (¾×, 1× or 1½× the estimate), the problem is reset and the clock starts from step 1; the same pill is then the countdown (amber under five minutes, red in the last minute), survives reloads, and ends the run early when clicked; its chevron opens the problem's run history and its tooltip names your best counted time. The run ends when every step is done; when the budget runs out you choose between ending it and keeping going, in which case the clock counts up (`+m:ss over`) and the run is recorded but not counted. A run *counts* only when the problem is completed within the budget with no solution revealed — that time appears on the problem's row; every run, newest first with how it ended, is one click away from the landing strip and from the pill.
- **Scratchpad** (`src/lib/scratchpad.ts`, `src/components/Scratchpad.tsx`): a whiteboard in a floating window over the playground (`⌘;` / `Ctrl+;`, or the pencil in the header) for sketching the system while building it — drag it by its title bar, resize or maximise it, keep reading the task and typing in the editor beside it. Boxes, ellipses and diamonds with centred labels (click to place one and type), arrows and lines that attach themselves to box outlines, freehand pen, text, an eraser; select, move, resize, drag connector ends, marquee-select, duplicate, nudge with the arrow keys; nine palette colours (the four concept hues among them), three widths, tinted fills, a dot grid with snapping; pan and zoom (wheel, pinch, space-drag); undo/redo; PNG export; and *course diagram*, which turns the problem's architecture diagram into editable boxes and arrows with the pane's routing and labels. One sketch per course (plus one for the landing page), persisted beside the workspaces.
- **Sharing and certificates** (`src/lib/social.ts`, `src/lib/certificate.ts`, `src/components/Social.tsx`, `src/pages/certificate/[course].tsx`): every badge toast, every earned badge in the catalog and every accepted step offers *Share on LinkedIn* — LinkedIn's composer opens prefilled with an editable post; nothing is posted on the learner's behalf. A course completed with every step accepted (no solution revealed) earns a **certificate**: a PNG drawn on a canvas (name, course, concepts, date, score, timed-run time, a certificate id), downloadable from the course page, with *Add to LinkedIn profile* (LinkedIn's certification deep link, filed under Licenses & certifications) and *Share on LinkedIn*. Each certificate has a public page, `/certificate/<course>?n=…&d=…&id=…`, pre-rendered per course with OpenGraph tags so the link unfurls; the learner's details travel in the query string and the id is a hash of them — there is no server and no record of learners. The name typed once is remembered.
- **Keyboard shortcuts** (`src/components/Shortcuts.tsx`): ⌘/Ctrl+⏎ submit, ⌘/Ctrl+B explorer, ⌘/Ctrl+\ problem pane, ⌘/Ctrl+; scratchpad, ⌥/Alt+] and ⌥/Alt+[ next and previous step, `?` for the list (also behind the keyboard button in the header).
- **Markdown export** (`src/lib/export.ts`): `⤓ download .md` on a course page saves its tutorial in the current language — statement, Mermaid architecture and sequence diagrams, tasks, checks, starters, hints and solutions behind `<details>` spoilers.
- **Persistence** (`src/lib/storage.ts`): attempts, language, per-step workspaces and per-course scratchpads live in IndexedDB (localStorage fallback) — per browser, no server.
- **Filesystem**: a course in a language is one virtual filesystem, one file per step (`thumb_server.py`, `thumb_cache.py`, …). The explorer beside the editor lists every file from step 1 with its status (✓ accepted, ◐ revealed, ○ open, 🔒 locked); clicking one opens it in a tab, VS Code style — tabs are the open files, closable with ×, and the step's own file opens itself when the step does. Every unlocked file is editable from any step and keeps its own undo history, so the code written in step 1 is there, as written, in step 2. The step's own file is marked with a dot and is the one Submit judges, whichever tab is active; `reset` restores the active file's starter. The explorer and the problem pane each fold away (the toggle left of the tabs, the `‹` in the pane header; a collapsed pane is a strip with the step title) and the choice persists with the layout in `localStorage` (`leetbuild:layout`).
- **Routes** (`src/pages/[[...slug]].tsx`): `/` is the problem list, `/<course>` reopens a course on the step last visited, `/<course>/<n>-<step>` addresses step n (numbered like its source file, e.g. `/image-cache/2-cache-aside`); every path is pre-rendered from the course data and anything else is a 404. Moving between them is ordinary navigation, so Back and Forward retrace your path while the playground stays mounted.
- **Diagrams** (`src/lib/layout.ts`): architecture diagrams are laid out automatically from the call graph (layered left to right, boxes sized to text, labels in the column gaps, long edges detoured around boxes, back edges arched over everything they span, the edges into and out of a box spread along its side so arrowheads never stack; wide diagrams keep a readable size and scroll sideways). Sequence diagrams are drawn from each step's `sequence`.
- **UI** (`src/components/`): the playground shell with LeetCode-style drag gutters (`SplitGutter`), the problem list and profile card, the problem/step pane, the verdict pane, the file tabs and CodeMirror step editor (`src/lib/editor.ts`), the diagrams, the Markdown dialect (`Markdown.tsx`: headings, callouts, lists, fenced code, tables, `:::widget name {json}`, `:::details`, pop quizzes), and `widgets/` (one component per infographic, registered in `widgets/index.tsx`).
- **Themes** (`src/styles/palette.ts`, `src/lib/theme.ts`): Night and Day are two palettes of one shape — Day keeps every Night hue with its lightness solved for the same WCAG contrast targets on white — emitted as CSS variables by `tailwind.config.ts`, so Tailwind classes, the CodeMirror theme and the SVG diagrams switch live. The sun/moon button in the header toggles them; the choice is saved in `localStorage` (`leetbuild:theme`), applied before first paint by an inline script in `_document.tsx`, and until one is made the OS preference applies.

## Content

Courses live in `src/data/problems/<NN>-<id>/`: `index.ts` holds the metadata, statement, architecture diagram (nodes, kinds and edges — placement is automatic), step order and the runtime **support modules** (`support.python`: generated protobuf code from `proto/*.proto` via `yarn protogen`, plus hand-written helpers in `support.ts`); `steps/<k>-<step-id>.ts` holds one step: task, sequence diagram, hints, checks, starter/solution code in all four languages, and the Python **harness** (`harness.python`, a module with `check_<id>(ctx)` per check; `ctx` is documented in `public/py/runtime/leetbuild/harness.py`). Courses are ordered in `src/data/problems/index.ts`; the content model is `src/lib/types.ts` and the widget catalog `src/lib/widgets.ts`. Generating protobuf modules needs `python3 -m pip install grpcio-tools==1.81.0` (its gencode matches the protobuf runtime Pyodide ships).

`yarn verify` (or `--problem <id>` / `--file <path>` / `--verbose` / `--no-runtime`) runs the judge's self-tests, checks every course's shape (including that no two steps of a course own the same file in any language, and that every check of a step with a harness has its `check_` function), asserts for every step in every language that the starter fails at least one static check (and at most one passes already) while the reference solution passes them all, boots the Python runtime in Node and asserts for every harness that the solution passes every runtime check while the starter does not, then checks that the course total is 1337.

Stacks the reference solutions use: Python — FastAPI, grpcio, confluent-kafka, redis-py · Go — net/http, google.golang.org/grpc, segmentio/kafka-go, go-redis v9 · Scala — Pekko HTTP, ScalaPB + grpc-java, kafka-clients, Jedis · C++ — cpp-httplib, grpc++, librdkafka, redis-plus-plus.

## Deploy

A plain Next.js 14 (pages router) app with no server-side state: deploy to Vercel or any Node host, or `next build` with static export. `NEXT_PUBLIC_SITE_URL` is optional: without it every share, certificate and export link is built from the page's own origin and the canonical/`og:url` tags are omitted; set it when the site answers on more than one origin (preview deployments, a vercel.app host beside a custom domain) so links and certificates always name the public one. The Python runtime is static too: `public/py/` ships the worker bundle (built by `prebuild`), the runtime's `.py` files and two vendored wheels, while Pyodide, its packages and PGlite are fetched by the browser from jsDelivr at first use.
