# LeetBuild — build systems, step by step

LeetCode for systems. Each course is a real system cut down to the parts that transfer — a URL shortener, a rate-limited API gateway, an image cache microservice, live chat fan-out, a notification service, a match engine, an online merchant transaction system, flash-sale inventory, a news feed, ride dispatch — built one file at a time in Python, Go, Scala or C++. Every step exercises one of four concepts: **HTTPS servers, gRPC, Kafka, Redis**.

A step gives you a task, a sequence diagram of the interaction, interactive infographics (TLS/HTTP lifecycle, status codes, idempotency keys, gRPC call types, deadlines and retries, Kafka partitions, consumer groups, delivery semantics, cache-aside and stampedes, token buckets, the transactional outbox, a limit order book), three progressive hints, and a revealable reference solution (plain or as a diff against your code). The architecture diagram highlights the components the step builds; click one to jump to its step.

## Run it

```sh
yarn install --ignore-engines   # node 22.10 is a hair below what one transitive eslint dependency declares
yarn dev                        # http://localhost:3000 (builds the runtime worker first)
yarn build && yarn start        # production
yarn verify                     # checks every course (see below); run after editing content
yarn verify --no-runtime        # the same without executing the Python harnesses
yarn lint                       # prettier + eslint
yarn compile                    # tsc --noEmit
yarn build:runtime              # rebuild public/py/worker.js after editing src/lib/runtime/
yarn protogen <course dir>      # regenerate a course's Python protobuf modules from proto/*.proto
```

Set `NEXT_PUBLIC_SITE_URL` (see `.env.example`) to the public origin when deploying: it is used for the canonical link and for the URLs inside shared result cards and exported Markdown. Without it, share links use the page's own origin.

## How it works

- **Python runs in the browser** (`src/lib/runtime/`, `public/py/`). A submission in Python is executed, not just pattern-matched: a Web Worker boots Pyodide (CPython in WASM, from the jsDelivr CDN, ~10 MB cached after the first run) into the LeetBuild runtime, which provides the infrastructure the courses talk to without a network — Redis through `fakeredis` on the virtual clock (TTLs, pub/sub, pipelines, GEO, and Lua scripts executed by a fengari VM on the JS side), an in-memory Kafka broker behind a `confluent_kafka`-shaped client (partitions, consumer groups, commits, delivery callbacks), gRPC over an in-process transport that generated `*_pb2_grpc` stubs and `grpc.aio` servers plug into (deadlines, latency and failure injection, streaming, cancellation), and real Postgres through PGlite. Each step's **harness** (`Step.harness.python`, one `check_<id>(ctx)` per check) exercises the learner's files — the whole course's filesystem is mounted, so cross-file imports resolve — and reports what it observed; the runtime verdict decides acceptance and the static pattern check survives only as an advisory *shape* chip. A run that cannot complete (runtime failure, 20 s budget) is reported, not counted as a wrong submission. The Python runtime itself lives in `public/py/runtime/` (plain `.py` files) and is shared with `yarn verify`, which runs every harness in Node.
- **The static judge** (`src/lib/judge.ts`) remains the verdict for Go, Scala and C++ and the advisory layer for Python. Every step lists named checks — properties a correct implementation has (the route, the TTL, the `NX` on the lock, the commit *after* the side effect) — as per-language patterns evaluated on comment-stripped code with `all` / `none` / `order` semantics. From the second wrong submission on a step, each failing static check also shows the shape the judge expects (`describeMatcher`); every step keeps a Submissions history.
- **Scoring** (`src/lib/scoring.ts`) is contest-like: 11 / 21 / 30 points per step by difficulty — the ten courses (56 steps) are worth exactly 1337 and `yarn verify` enforces it — −20% per hint, −5% per wrong submission (floor 25%), 0 for a revealed step. Totals roll up into a guild rank (Novice → Apprentice → Journeyman → Artificer → Master Artificer → Archmage, by share of all points), solved counts by difficulty and per-concept mastery. Steps unlock in order; a course can be started over.
- **Game layer** (`src/lib/gamify.ts`, `src/components/Badges.tsx`): 17 badges in five tracks (Milestones, Craft, Mastery, Habit, Languages), each with measurable *progress* ("Kafka master 3/16", "Shipped 4/6 · Image Cache") — a badge is earned exactly when its progress completes, badges are never revoked, and fresh ones are announced with toasts; a daily streak; progress to the next rank; confetti on every fresh accept; a Wordle-style result card copied to the clipboard with `⇪ share`. The landing page keeps all of this to one strip — points inside a rank ring, the streak with what to do about it, the badges earned, one row of concept mastery — with the full catalog (closest badges first) and the secondary stats one click away, so the problems stay above the fold.
- **Markdown export** (`src/lib/export.ts`): `⤓ download .md` on a course page saves its tutorial in the current language — statement, Mermaid architecture and sequence diagrams, tasks, checks, starters, hints and solutions behind `<details>` spoilers.
- **Persistence** (`src/lib/storage.ts`): attempts, language and per-step workspaces live in IndexedDB (localStorage fallback) — per browser, no server.
- **Filesystem**: a course in a language is one virtual filesystem, one file per step (`thumb_server.py`, `thumb_cache.py`, …). The explorer beside the editor lists every file from step 1 with its status (✓ accepted, ◐ revealed, ○ open, 🔒 locked); clicking one opens it in a tab, VS Code style — tabs are the open files, closable with ×, and the step's own file opens itself when the step does. Every unlocked file is editable from any step and keeps its own undo history, so the code written in step 1 is there, as written, in step 2. The step's own file is marked with a dot and is the one Submit judges, whichever tab is active; `reset` restores the active file's starter. The explorer and the problem pane each fold away (the toggle left of the tabs, the `‹` in the pane header; a collapsed pane is a strip with the step title) and the choice persists with the layout in `localStorage` (`leetbuild:layout`).
- **Routes** (`src/pages/[[...slug]].tsx`): `/` is the problem list, `/<course>` reopens a course on the step last visited, `/<course>/<n>-<step>` addresses step n (numbered like its source file, e.g. `/image-cache/2-cache-aside`); every path is pre-rendered from the course data and anything else is a 404. Moving between them is ordinary navigation, so Back and Forward retrace your path while the playground stays mounted.
- **Diagrams** (`src/lib/layout.ts`): architecture diagrams are laid out automatically from the call graph (layered left to right, boxes sized to text, labels in the column gaps, long edges detoured around boxes; wide diagrams keep a readable size and scroll sideways). Sequence diagrams are drawn from each step's `sequence`.
- **UI** (`src/components/`): the playground shell with LeetCode-style drag gutters (`SplitGutter`), the problem list and profile card, the problem/step pane, the verdict pane, the file tabs and CodeMirror step editor (`src/lib/editor.ts`), the diagrams, the Markdown dialect (`Markdown.tsx`: headings, callouts, lists, fenced code, tables, `:::widget name {json}`, `:::details`, pop quizzes), and `widgets/` (one component per infographic, registered in `widgets/index.tsx`).
- **Themes** (`src/styles/palette.ts`, `src/lib/theme.ts`): Night and Day are two palettes of one shape — Day keeps every Night hue with its lightness solved for the same WCAG contrast targets on white — emitted as CSS variables by `tailwind.config.ts`, so Tailwind classes, the CodeMirror theme and the SVG diagrams switch live. The sun/moon button in the header toggles them; the choice is saved in `localStorage` (`leetbuild:theme`), applied before first paint by an inline script in `_document.tsx`, and until one is made the OS preference applies.

## Content

Courses live in `src/data/problems/<NN>-<id>/`: `index.ts` holds the metadata, statement, architecture diagram (nodes, kinds and edges — placement is automatic), step order and the runtime **support modules** (`support.python`: generated protobuf code from `proto/*.proto` via `yarn protogen`, plus hand-written helpers in `support.ts`); `steps/<k>-<step-id>.ts` holds one step: task, sequence diagram, hints, checks, starter/solution code in all four languages, and the Python **harness** (`harness.python`, a module with `check_<id>(ctx)` per check; `ctx` is documented in `public/py/runtime/leetbuild/harness.py`). Courses are ordered in `src/data/problems/index.ts`; the content model is `src/lib/types.ts` and the widget catalog `src/lib/widgets.ts`. Generating protobuf modules needs `python3 -m pip install grpcio-tools==1.81.0` (its gencode matches the protobuf runtime Pyodide ships).

`yarn verify` (or `--problem <id>` / `--file <path>` / `--verbose` / `--no-runtime`) runs the judge's self-tests, checks every course's shape (including that no two steps of a course own the same file in any language, and that every check of a step with a harness has its `check_` function), asserts for every step in every language that the starter fails at least one static check (and at most one passes already) while the reference solution passes them all, boots the Python runtime in Node and asserts for every harness that the solution passes every runtime check while the starter does not, then checks that the course total is 1337.

Stacks the reference solutions use: Python — FastAPI, grpcio, confluent-kafka, redis-py · Go — net/http, google.golang.org/grpc, segmentio/kafka-go, go-redis v9 · Scala — Pekko HTTP, ScalaPB + grpc-java, kafka-clients, Jedis · C++ — cpp-httplib, grpc++, librdkafka, redis-plus-plus.

## Deploy

A plain Next.js 14 (pages router) app with no server-side state: deploy to Vercel or any Node host, or `next build` with static export. Set `NEXT_PUBLIC_SITE_URL` in the environment. The Python runtime is static too: `public/py/` ships the worker bundle (built by `prebuild`), the runtime's `.py` files and two vendored wheels, while Pyodide, its packages and PGlite are fetched by the browser from jsDelivr at first use.
